How the Admin Page Routes Work

Most Admin submenu items navigate to /admin/{Data}, which is handled by a single page: Adm/Club/Admin.razor + Adm/Club/Admin.razor.cs. The route parameter Data selects the operation inside OnParametersSetAsync() via a switch expression: 

string com = Data switch
{
    "backup"        => Backup(),
    "images-import" => await ImagesProcessAsync(),
    "club-import"   => await ImportClub(),
    "restore"       => Restore(),
    "excel"         => await Excel(),
    "deletemonth"   => await DeleteMonth(),
    _               => null
};

On every visit, OnInitialized() calls DirectoryPrepare(gData.ImportDirectory), which creates wwwroot\Import\ if missing and deletes every file in it — the staging area always starts clean. The page renders a ProgressBar, a white Messages list, and a red Errors list, plus two conditional UI blocks: the photo-removal chooser (used by Import Club) and the <Backup> file-pick component (used by Backup/Restore).

1. Images Process — In-Depth Analysis

/admin/images-import  →  Admin.ImagesProcessAsync() in Adm/Club/Admin.razor.cs (region ImagesProcess, the second half of the file).

This is the monthly photo-publishing pipeline: it takes the zipped photo exports from PhotoVault and turns them into web-ready club photos, published in two places at once — the local website copy on disk and the remote Absolute Hosting server. The whole feature is five sequential stages orchestrated by one driver method, with live progress reporting and per-file error collection along the way. 

FileUpload (dialog)                 wwwroot\Import\*.zip
        │ unzip
        ▼
D:\BKK\Inbox\Club\Photos\{yyyy-MM}\*.jpg          (originals, any filename)
        │ copy + rename to 7-digit ID
        ▼
D:\BKK\Inbox\Club\Photos\{yyyy-MM}\Temp\#######.jpg
        │ resize (max 1365×768, aspect kept)
        ▼
D:\BKK\Inbox\Club\Photos\WEB\#######.jpg          (web previews)
        │ zip ──────────────►  {Downloads}\ZippedExport\BKK-{yyyy-MM}.zip ──► POST {Api}FU/zip
        │ copy + delete
        ▼
{LocalWebsitePath}wwwroot\ClubPhotos\{yyyy-MM}\#######.jpg   (local website)

The driver — ImagesProcessAsync()

Wires up progress, runs the five stages strictly in sequence (each one awaited), and appends the completed stage name to the white Messages list as it goes: 

IProgress<ProgressInfo> progress = new Progress<ProgressInfo>(value =>
{
    Info = value;
    StateHasChanged();
});
Filename = await PhotosLocalUnzipAsync(progress);   // null ⇒ user cancelled ⇒ abort, no error
await PhotosCopyRenameAsync(progress, Filename);
await PhotosGeneratePreviewsAsync(progress, Filename, 1365, 768);
await PhotosZipAsync(progress);
await UploadToHosting(progress, $"{gData.Downloads}ZippedExport\\BKK-{Filename}.zip");
  • Progress plumbing: Progress<T> captures the Blazor synchronization context at construction, so worker threads can call progress.Report(...) from Task.Run / Parallel.ForEachAsync and the callback still runs on the UI thread — that's why a bare StateHasChanged() (no InvokeAsync) is safe here. Each report carries a ProgressInfo with CurrentStage, Current, Total, Percentage and Message, rendered by the <ProgressBar> component at the top of the page.
  • Cancellation path: if you close the upload dialog, PhotosLocalUnzipAsync returns null and the run ends silently — nothing has been written yet at that point.
  • Error path: the body is wrapped in try/catch that rethrows (throw new Exception($"Error during image processing: ...", ex)). Because the caller is OnParametersSetAsync's switch, which has no catch of its own, a mid-pipeline failure surfaces as an unhandled circuit exception (Blazor's yellow error bar) rather than in the page's red Errors list. The finally block always hides the progress bar.
  • State used across stages: the chosen name is kept in the component-level Filename property — stages 2–5 all derive their paths from it.
The folder name matters. The name you enter in the upload dialog becomes the photo folder name and the zip name. It must be the year-month in YYYY-MM form, because the rest of the app builds photo URLs as ClubPhotos/{date.toYear_Month_Digits()}/{IntRef}.jpg (see Extensions.toPhotosView) — e.g. ClubPhotos/2026-06/1234567.jpg. A differently-named folder uploads fine but the site will not find the images.

Stage 1 — PhotosLocalUnzipAsync(IProgress<ProgressInfo>)

returns Task<string> — the chosen folder/zip name, or null on cancel

  1. Calls FileUpload() → state.ShowFileUpload("ZIPPED PHOTOS", "Upload Zipped Photos from PhotoVault", gData.ImportDirectory). The shared FileUpload component (hosted in MainLayout) handles the dialog; the selected .zip files (typically 3 — one per PhotoVault export part) are saved into wwwroot\Import\, which OnInitialized() had already wiped via DirectoryPrepare, so only this run's zips are present.
  2. Enumerates Directory.GetFiles(gData.ImportDirectory, "*.zip") — note it processes every zip in the staging folder, not just the ones the dialog returned (safe only because the folder was cleaned).
  3. Creates the destination {gData.photosLocal}{Filename} (= D:\BKK\Inbox\Club\Photos\2026-06) and turns the progress bar on (progressBar.IsVisible = true).
  4. Extracts each zip with ZipFile.ExtractToDirectory(zipPath, dest, overwriteFiles: true) inside Task.Run (keeps the UI thread responsive), reporting i+1 / totalZips between files. The overwriteFiles: true makes re-runs of the same month idempotent — extracting again just overwrites.

Stage 2 — PhotosCopyRenameAsync(IProgress<ProgressInfo>, string fn)

source: {photosLocal}{fn}\*.jpg → dest: {photosLocal}{fn}\Temp\#######.jpg

PhotoVault filenames embed the photo's 7-digit internal reference. This stage normalises every file to exactly {IntRef}.jpg — the contract the whole site depends on, since Photo.IntRef from the club import is what links a database row to its image file.

  • Extraction: Regex.Match(originalName, @"\d{7}") — the first run of exactly 7 digits anywhere in the name. A file with no 7-digit run is skipped, not fatal: a "Skipped — no 7-digit ID in filename" entry is added to the red Errors list and the run continues.
  • Concurrency: one Task.Run per file, awaited together with Task.WhenAll. The shared progress counter uses Interlocked.Increment, so the "Processed n/total" numbers are race-free. Errors.Add is called from worker threads (a List<string> is not thread-safe — in practice collisions are rare since errors are the exception, but it is the one spot in the stage that isn't synchronised).
  • File.Copy(..., overwrite: true) — the originals stay behind in the month folder as the archive copy; Temp\ is the working set for the next stage. Per-file failures are caught and logged, never thrown.
  • Subtlety: GetFiles(sourceDir, "*.jpg") is top-level only and case-insensitive on Windows (.JPG works), but a zip that nests its images one folder deeper would yield 0 files here — the stage would report "Found 0 files" and the pipeline would continue with nothing.

Stage 3 — PhotosGeneratePreviewsAsync(IProgress<ProgressInfo>, string fn, int width, int height, int degreeOfParallelism = 0)

source: {photosLocal}{fn}\Temp\ → dest: {photosLocal}WEB\  •  called with 1365×768

  • CPU-bound image work is parallelised with Parallel.ForEachAsync; MaxDegreeOfParallelism defaults to Environment.ProcessorCount (the optional parameter lets a caller throttle it, but the pipeline call leaves it at 0 ⇒ CPU count).
  • Each file goes through GenerateImagesAsync(source, destination, width, height): 
    using var image = await Image.LoadAsync(source);          // SixLabors.ImageSharp
image.Mutate(x => x.Resize(new ResizeOptions
{
    Mode = ResizeMode.Max,                                  // fit inside 1365×768, keep aspect
    Size = new Size(width, height)
}));
await image.SaveAsync(destination);                         // format inferred from .jpg extension
    ResizeMode.Max never crops and never upsizes the proportions wrongly: a 6000×4000 landscape becomes 1152×768 (height-bound); a portrait 3000×4500 becomes 512×768. The original full-resolution file in Temp\/month folder is untouched — only the web copy is reduced.
  • Error semantics differ from stage 2: here a single bad image (corrupt file, unsupported format) throws, Parallel.ForEachAsync cancels its remaining work, and the exception bubbles up through ImagesProcessAsync — the run stops. Stage 2 tolerates bad files; stage 3 does not.
  • WEB\ is a shared folder (not per-month). It is normally empty at this point because stage 4 of the previous run deleted everything it copied — but if an earlier run died between stages 3 and 4, leftovers from that run would be swept into this month's zip and website copy.

Stage 4 — PhotosZipAsync(IProgress<ProgressInfo>)

returns "Successfully zipped {n} photos to {zipPath}"

  1. Computes its four paths from Filename:
    VariableValueRole
    sourceDir{photosLocal}WEB\previews from stage 3
    zipPath{Downloads}ZippedExport\BKK-{Filename}.zipupload artifact for stage 5
    rootdestwwwroot\ClubPhotos\{Filename}\ (relative)created in the running app's folder
    localWebDest{LocalWebsitePath}wwwroot\ClubPhotos\{Filename}\= D:\VS\VS Active\BCCBlazor\BCC\wwwroot\ClubPhotos\{Filename}\
  2. Deletes any existing BKK-{Filename}.zip, then ZipFile.CreateFromDirectory(sourceDir, zipPath) on a background task — the zip is created before the copy loop, so it always contains the complete WEB set.
  3. Then loops the previews one by one: File.Copy to localWebDest (overwrite) followed immediately by File.Delete of the WEB copy — so a fully successful stage leaves WEB\ empty, which is what makes the shared folder safe for the next month's run.
Two destinations, one copy. Note that rootdest (the relative wwwroot\ClubPhotos\{Filename}\ inside this BCCPunte app) is created with Directory.CreateDirectory but no files are copied into it — the copy loop only targets localWebDest, i.e. the separate BCCBlazor website project. The BCCPunte app itself gets an empty month folder; its own photo display relies on whatever populates its ClubPhotos separately. Keep this in mind if local photos ever appear missing for a new month.

Stage 5 — UploadToHosting(IProgress<ProgressInfo>, string filePath)

Pushes the zip to the live server, which (per the menu tooltip) lands it in \wwwroot\Import\yyyy.mm.zip on Absolute Hosting for the remote site to unpack.

  1. Pre-flight checks (each fails soft — a ❌ line in Messages, return, no exception): must end in .zip, must exist on disk, must be ≤ 120 MB (fileInfo.Length > 120L * 1024 * 1024). 120 MB is the matching server-side limit — if a month's previews exceed it the upload is refused locally and you would need to split the month or upload manually.
  2. HTTP setup: gData.CreateUploadClientHandler() returns a plain HttpClientHandler in production; only when gData.Api contains "localhost" does it accept self-signed certificates (dev convenience). client.Timeout = TimeSpan.FromMinutes(15) — sized for a 100 MB+ upload on a slow uplink.
  3. Authentication — Login(HttpClient): reads Auth:Username / Auth:Password from configuration (appsettings.json; no user secrets in this project), POSTs them as JSON to {Api}Auth/login, and expects a LoginResponse {{ Token }}. A non-success status or missing token throws with the server's error text — and because this throw happens inside stage 5's outer try only covers the POST, a login failure propagates up and ends the run via the driver's catch.
  4. Upload: MultipartFormDataContent with one part named "file" wrapping a StreamContent(File.OpenRead(filePath)), sent with Authorization: Bearer {token} to {gData.Api}FU/zip. The result is reported verbatim: ✅ with the server's response body on success, ❌ with status code + reason + body on failure; transport exceptions are caught and logged with their inner exception. This stage shares its Login/upload logic pattern with the standalone Upload to AbsHosting page, which adds the FU/html route for .html files.

Failure-mode summary

StageSingle bad fileWhole-stage failureSafe to re-run?
1. Unzipn/aException ends run (e.g. corrupt zip)Yes — overwriteFiles: true
2. Copy/RenameLogged to Errors, skippedOnly if directory enumeration failsYes — copy with overwrite
3. PreviewsThrows — ends the runException ends runYes — but check WEB\ for leftovers first
4. Zip + publishException ends runException ends runYes — old zip deleted first; copies overwrite
5. Uploadn/a❌ message (soft) — except login failure, which throwsYes — server overwrites the month zip

Practical recovery rule: because every stage is overwrite-safe and stage 1 re-extracts from the original zips, the simplest fix after any mid-pipeline failure is to resolve the cause (e.g. delete the corrupt jpg from the month folder) and run Images Process again from the top with the same name. The only cleanup worth checking manually is D:\BKK\Inbox\Club\Photos\WEB\ — it should be empty before a fresh run.

2. Import Club

/admin/club-import  →  Admin.ImportClub() in Adm/Club/Admin.razor.cs (region ClubImport). This is the main entry route for monthly club competition imports — the most involved feature in the app.

Entry logic — ImportClub()

  1. If gData.lastDateClubImported.Month == 9 (September was last imported) → it's year-end: calls YearEnd() → OctoberMonth(), which runs ds.LastDates(), ds.Promotion_Due() and DatesStoreInDb() with no file import ("October month with no Imports, but Promotions succesfully done").
  2. Otherwise opens the upload dialog (state.ShowFileUpload("CLUB IMPORT", ...)). The filename decides the path:
    • starts with Scoresheet → ImportScores(fn)
    • starts with Results → ImportResults(fn)
    • anything else → exception: "File Name is not correct".

CSV parsing infrastructure

MethodWhat it does
Import(fn)Refreshes gData dates via ds.LastDates(), then finds the uploaded file in wwwroot\Import\ by wildcard match.
TextFieldParserInitialize(p)Reads the header line (lower-cased) into Headers, configures the VB TextFieldParser as comma-delimited with whitespace trimming.
SetScoreIndices() / SetResultIndices()Pre-computes the column index of every required header once (e.g. _si_score = Headers.IndexOf(ScoreHeaders.ScoreTotal)) so row parsing is index-based, not name-based.

Then peeks the first data row, extracts the 7-digit IntRef, and returns whether that photo already exists for the current club year — i.e. "has this month already been imported?"

Path A — ImportScores(filename)

  1. Parse all rows with processLineScores(fields) (see below).
  2. If HeadersCheckScores says the month was already imported → switch to score-update mode: UpdateScores(file) instead (matches each row by IntRef and fills in Photo.Score; throws "Scores already Present" if the first photo already has a score > 0).
  3. Group photos by PVID (PhotoVault member ID). For each member: GetMasterRow(photo) finds the Master, and ds.GetLastMonthly(master) finds/creates the month's Monthly row; all of that member's photos get its MonthlyID.
  4. PhotoQuantity(photos) — enforces entry limits (see below) with an interactive chooser.
  5. Bulk-insert via repo.CreateScope() → scope.AddRange(photos) → SaveChangesDetachAsync().
  6. Post-processing: MonthlyUpdate() → MonthlyCompute() → ds.Promotion_Due() → DatesStoreInDb() → ds.CleanImportDirectory().

processLineScores(string[] data) — one CSV row → one Photo

  • Reads Category, PVID, Honours, Email, Title, IntRef, Score from the pre-computed indices.
  • Rating map: "Golden Honours"→6, "Galaxy"→7, otherwise the numeric value.
  • Star group: rating 1–2 → group 1, 3 → 2, 4–5 → 3, else 4.
  • Winner flags from the Awards column: ~word~ → both Winner and Club_Winner; a single ~ → Club_Winner if the text contains "IC", else Winner.
  • Award = first word character of the awards string (C/G/S/B).
  • Category stays "S" (Set Subject) as-is; otherwise it becomes {Category}{Star_Group} (e.g. P3, N1).

Path B — ImportResults(filename)

  1. Parse all rows with processLineResults(fields, photos) — same rating/star-group mapping; "com" award is normalised to "C"; lastname "DeBeer" is fixed to "De Beer"; no PVID/Score columns in this format.
  2. If already imported → just reports "Already Imported Scoresheet into DB".
  3. Winner reconciliation: rows are grouped by IntRef; when a photo appears more than once the duplicate rows carry the winner codes — Award == "CW" sets Club_Winner, any other multi-char award sets Winner on the single-char base row. Then only base rows (Award.Length == 1) are kept.
  4. Members are resolved by Name (no PVID in this file) via GetMasterRow + ds.GetLastMonthly, then the same PhotoQuantity → bulk insert → post-processing chain as Path A.

Member resolution

MethodWhat it does

Entry limits — PhotoQuantity(IList<Photo>)

Rule: per member per month, max 3 photos where Category ≠ "S" and max 2 where Category = "S". Members over the limit have all their photos shown in the on-page chooser (the red-bordered panel in Admin.razor). The import code literally pauses on a TaskCompletionSource<bool> until you tick the photos to delete and click "Remove the ticked photos and continue import" (ConfirmPhotoRemovals(true)) or cancel (ConfirmPhotoRemovals(false) → empty list, "Import cancelled by user"). SetAllRemovalFlags(bool) backs the Tick all / Untick all buttons.

Points engine

MonthlyUpdate() — award counts from this month's photos

For every photo of the latest month (Category not "S"/"PH"): award C → Mm+1 (Com), G → Gm+1, S → Sm+1, B → Bm+1. For Set Subject photos ("S") the award goes straight to VO points (VOm): C=5, G=3, S=2, B=1.

MonthlyCompute() — running totals

FieldComputation
Pm (points/month)Mm×5 + Gm×3 + Sm×2 + Bm×1
Mg, Gg, Sg, BgCumulative award counts per grade (since last promotion)
GMpMg + Gg (Gold-or-better count toward promotion)
PpCumulative promotion points (Pp + Pm)

All additions use the AddNull() extension — nullable ints where 0 collapses back to null.

DatesStoreInDb()

Writes the newest Monthly date into the Datum row lastImport (a September date is bumped to October), updates gData.lastDateClubImported, and when the new month is November also resets the clubYearStart Datum / gData.lastDateClubYear.

4. Word

/worddoc → Pages/WordDoc.razor.cs, method OnFileSelected(InputFileChangeEventArgs). Converts a chosen Microsoft Word document to HTML and publishes it under the Info menu.

  1. Validates the upload: must be .docx, max 25 MB (MaxUploadBytes).
  2. Copies the browser stream into a MemoryStream and opens it with DocumentFormat.OpenXml (WordprocessingDocument.Open).
  3. Converts to HTML with OpenXmlPowerTools HtmlConverter.ConvertToHtml (CSS classes prefixed docx-, fabricated automatically).
  4. Wraps the result in a full HTML page linked to /styles.css. Special case: files named Program (Afr).docx / Program (Eng).docx get the Venue + Program images injected above the content.
  5. Saves to wwwroot/html/{name}.html and navigates to /info/{name} — which is also how the converted document appears in the Info menu (built from the files in that folder).

Errors surface through state.ShowMessageAsync("Word conversion failed", ...).

6. Backup DB

/admin/backup → Admin.Backup() sets Title = "Backup" and filePick = true, which renders the Adm/Club/Backup.razor component inside the Admin page.

  1. The Backup component's OnInitialized() lists all *.bak files in gData.backupPath (C:\Users\Lamps\OneDrive\Database\SQL16\Backup\BCC\).
  2. You either pick an existing file name or type a new one; Submit() fires the ecbBackup EventCallback with {name}.bak. (Pressing Enter in the textbox turns the button red via keyDownText as a "you're about to overwrite/act" cue.)
  3. Back in Admin, ecbBackup(file) deletes any existing file of that name, then calls repo.SqlBackupAsync(fn).

Repo.SqlBackupAsync(fn)

Use BCC Backup Database BCC to Disk = {fn} with init

Executed via ExecuteSqlInterpolated on a background task. WITH INIT overwrites the backup set. Success adds "Success in Backingup DB" to Messages; exceptions land in the red Errors list with stack trace.

7. Restore DB

/admin/restore → Admin.Restore(): if {Downloads}bcc.bak exists it is first moved into gData.backupPath (so a freshly-downloaded production backup is immediately offered), then the same Backup.razor component is shown in Restore mode.

Choosing a file fires ecbRestore(file) → repo.SqlRestoreAsync(fn):

USE master;
ALTER DATABASE [BCC] SET SINGLE_USER WITH ROLLBACK IMMEDIATE;
RESTORE DATABASE [BCC] FROM DISK = @filePath WITH REPLACE;
USE master;
ALTER DATABASE [BCC] SET MULTI_USER;
Destructive: WITH REPLACE overwrites the live database and SINGLE_USER WITH ROLLBACK IMMEDIATE kicks out all other connections. Make sure you picked the right .bak.

8. Excel

/admin/excel → Admin.Excel(). Despite the name it writes CSV archives (openable in Excel) — one snapshot file per month from 2013-11-01 to today.

  1. Loads all Masters and all Monthlies in the range once, groups Monthlies per member and sorts by date.
  2. Walks month by month, advancing a per-member index (amortised O(1)) so that for each month every member contributes their latest Monthly on or before that date.
  3. Each month's snapshot goes to CsvWrite(ms, dat); progress is shown via state.ShowProgress("EXCEL") / UpdateProgress.

CsvWrite(IList<Monthly>, DateOnly)

Writes D:\BKK\ARCHIVES\Ou punte rekords\{Year}\{date}.csv with header Date,Name,Grade,VOm,Mm,Gm,Sm,Bm,Pm,Salm,Mg,Gg,Sg,Bg,GMp,Pp,Salp,GMy,Py,VOy,Saly — creating the year folder as needed and skipping files that already exist (so re-runs only fill gaps).

9. Delete Month

/admin/deletemonth → Admin.DeleteMonth(). Rolls back the last imported month from the database while leaving the image files on disk intact (per the menu tooltip).

  1. Cutoff = gData.lastDateClubImported.AddMonths(-1); everything dated after the cutoff goes.
  2. Inside a single RepoScope transaction (BeginTransactionAsync): deletes the month's Photo rows, then the Monthly rows, then Salon entries belonging to SalonMasters after the cutoff, then those SalonMasters — each batch followed by SaveChangesDetachAsync().
  3. DatesStoreInDb() recomputes lastImport from what is now the newest Monthly.
  4. Re-syncs each member's current grade: for the (new) last month, Master.RatingID = Monthly.RatingID — undoing any promotions the deleted import had applied.
  5. CommitAsync() on success; any exception triggers RollbackAsync() and returns the error message, leaving the database untouched.
